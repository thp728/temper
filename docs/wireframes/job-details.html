Why this configuration

These are the decisions Temper made for you, and the alternatives that lost; the configuration this job froze.

method qlora

The trainer can execute qlora today, and selection picks the cheapest executable method that fits; price never depends on method, so a method that loses here loses on footprint (full fine-tuning rewrites every weight; an adapter is cheaper to fit), not on price.

▶ Alternatives considered (2)
hardware L4

Predicted peak is 7.8 GB; the L4 (24.0 GB) is the cheapest card currently available that holds it with 16.2 GB to spare.

▶ Alternatives considered (4)
device count 1

One L4 holds the predicted peak of 7.8 GB. Qlora has never run sharded, so extra cards replicate the same per-device footprint rather than shrinking it, and only add interconnect overhead and cost.

▶ Alternatives considered (2)
disk 100 GB

Weights at download precision (16.4 GB) + retained checkpoints (0.5 GB) + trainer image (8.5 GB) + working space (10.0 GB, an assumed allowance) = 35.4 GB raw, floored at platform minimum of 100 GB.

▶ Alternatives considered (1)
precision nf4 (4-bit)

Qlora quantises the frozen base to NF4 at 0.5 bytes/param, cutting the weights pool from 16.4 GB (bf16) to 4.1 GB — the difference between fitting the L4 and renting something bigger.

▶ Alternatives considered (1)
sequence length 2048

The trainer default (2048, trainer-defaults.json), well inside the model's 40960 context so no row is truncated against the context limit; activation memory (0.6 GB at this length) is the memory budget the hardware was chosen against.
