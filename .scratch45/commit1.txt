A dataset can be imported from a public repository, through the same validation path

Closes #45 (backend). Users start from a reference -- a public dataset
repository, optionally a configuration and a split -- instead of preparing a
file. The imported rows go through exactly the same streaming validation as an
upload: same schema detection, same line-numbered errors, same thinking-mode
detection. There is one validator (`validation.validate_chunks` consumes
whatever bytes it is given); the only new thing is a seam that turns a remote
repository into the same bytes an upload would have carried.

Why this shape:

- The remote-datasets seam (`remote_datasets.py`) lives in the control plane
  for the same reason the model-facts seam does: resolving an arbitrary public
  dataset is network I/O, and the core package carries none. The seam resolves
  the reference up front -- a repository that cannot be fetched, a
  configuration that must be named, a split that does not exist, or a split
  that resolves to nothing is refused with its reason as a coded 400 before
  anything is stored, never left to fail mid-fetch. The one way a fetch can
  die is part-way through streaming, and that surfaces as a coded
  `fetch_failed` 400 with the partial row deleted.
- Flat memory holds for imports: rows are fetched one bounded page (100 rows,
  the datasets-server cap) at a time and serialised into bounded chunks
  (`jsonl_chunks`), so peak memory does not scale with the dataset. Nothing is
  fetched whole before validating.
- The size ceiling applies to imports by reading `config.MAX_DATASET_BYTES`
  (ADR-0036, never a retyped number) and enforcing it mid-stream, the same
  refusal a lying Content-Length earns on an upload. A remote reference has no
  declared size, so there is nothing to refuse on ahead of time.
- An import that fails validation is still stored with its report: the bytes
  go to object storage and `_validate_in_background` runs on them exactly as
  for an upload, so the report the user sees names the rows to fix.
- The test suite and browser journeys run against a local double
  (`fake_remote_datasets.py`), the datasets-seam equivalent of FakeProvider:
  no test or journey reaches the network.

Alternative rejected: a second, import-specific validation implementation.
The issue's central sentence forbids it -- "nothing gets a shortcut for
arriving over a network" -- so the seam produces bytes and the existing
validator consumes them. Another rejected alternative: materialising the
remote dataset to memory to re-validate later; the streaming pass is the whole
point, and an import is exactly as large as an upload.
